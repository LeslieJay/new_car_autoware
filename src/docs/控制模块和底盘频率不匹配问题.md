• 结论：当前实测 `/control/command/control_cmd` 为 50 Hz，VCU 协议同样要求 50 Hz。CAN driver 仍使用独立的 20 ms 周期发送层，在每个 CAN 周期发送当时最新的控制指令，以隔离 ROS 调度抖动并避免旧指令积压。

  ## 当前频率链路

  ### Vehicle Command Gate

  配置中的：

  update_rate: 10.0

  主要控制 gate 的状态检查、急停检查、挡位、转向灯等定时任务。

  正常自动驾驶的 Control 指令不是由该 10 Hz 定时器发布，而是在收到上游控制指令时立即发布：

  上游控制器
    → onAutoCtrlCmd()
    → publishControlCommands()
    → /control/command/control_cmd

  当前轨迹跟踪器 `ctrl_period: 0.02`，因此正常自动驾驶链路的目标频率为50 Hz。实际频率仍应通过 `ros2 topic hz` 验证，不能只根据 `vehicle_cmd_gate.update_rate` 判断。

  相关实现：src/universe/autoware_universe/control/autoware_vehicle_cmd_gate/src/vehicle_cmd_gate.cpp:387

  ### CAN driver

  CAN driver 收到一条 `/control/command/control_cmd` 后编码并替换最新的 `0x201`：

  Control callback → 编码0x201 → 替换latest_control_frame

  CAN发送线程使用 `steady_clock` 独立保持20 ms节拍：

  每20 ms → 读取latest_control_frame → 发送0x201

  普通 `0x301/0x401` 等事件帧仍走FIFO。即使ROS和CAN都是50 Hz，也不要求两者相位对齐；每个CAN周期只发送当时最新值。

  ## 修改前可能出现的问题

  ### 1. VCU报文超时

  如果 VCU 把 20 ms 当成必须满足的通信周期，当前可能出现：

  - 控制报文超时
  - 驱动使能退出
  - 速度指令间断
  - 周期性减速、抱闸或停车
  - VCU故障码或通信故障

  具体是否在20 ms后立即超时，需要确认 VCU 的超时门限。

  ### 2. Byte5/Byte6物理含义失真

  现在确认 Byte5/Byte6 表示每个20 ms周期的电机目标转速增减量。

  如果 Byte=1：

  每20 ms目标转速增加1 r/s
  1秒共50个周期
  最终增加50 r/s

  修改前如果只在10 Hz收到新帧，并且 VCU仅在收到帧时执行一次增量，那么1秒只执行10次：

  期望：50 r/s
  实际：10 r/s

  加减速会变成预期的五分之一，之前基于50 Hz得到的标定系数也会失效。

  如果 VCU内部以50 Hz持续使用最后一帧，则加速度不会缩小，但仍然存在报文超时和心跳风险。这个行为需要实车或台架确认。

  ### 3. 控制延迟增加

  修改前10 Hz Control 本身带来最多约100 ms的采样等待，再叠加旧发送线程最多约60 ms等待：

  最坏新增等待可能接近160 ms

  会影响：

  - 停车距离
  - 障碍物响应
  - 终点停车精度
  - 转向跟踪
  - 低速控制稳定性

  ### 4. CAN帧突发发送

  旧发送线程每60 ms调用一次 `pop_all()`。如果这段时间收到多条控制指令，旧指令不会被合并，而是被连续写入CAN。

  结果可能是：

  长时间无0x201 → 短时间连续多帧 → 再次长时间无帧

  平均频率即使看起来正常，周期抖动仍然很大。VCU可能依次执行已经过时的中间命令。

  ### 5. 急停更新不够及时

  普通控制指令是回调驱动的，但部分急停逻辑受 gate 的10 Hz定时器控制。再叠加CAN发送线程等待，紧急控制生效时间可能进一步增加。

  ## 推荐方案

  ### 方案一：CAN driver独立50 Hz周期发送

  这是推荐方案。

  将 ROS 控制频率和 CAN 协议频率解耦：

  Autoware Control，50 Hz
          ↓
  CAN driver收到后只更新“最新控制状态”
          ↓
  独立20 ms定时线程
          ↓
  始终发送最新0x201，固定50 Hz

  核心原则：

  - Control callback只负责解析、限幅、编码并替换最新 0x201。
  - 不再把每一条 0x201 放入普通FIFO队列。
  - CAN发送线程用 steady_clock 每20 ms发送一次最新 0x201。
  - 连续收到多条Control时只保留最新一条，丢弃过期中间值。
  - 0x301、0x401等事件型报文仍可使用普通队列。
  - Byte5/Byte6随最新控制指令更新；ROS 与 CAN 不要求相位对齐。
  - 不在CAN driver内插值速度；速度斜坡由VCU依据Byte5/Byte6执行。

  建议参数：

  control_frame_period_ms: 20
  control_command_warn_timeout_ms: 60
  control_command_stop_timeout_ms: 100

  ### 指令超时保护

  CAN driver应保存最后一条Control的接收时间。

  建议状态：

  指令年龄 <60 ms：
    50 Hz发送最新控制帧

  60–100 ms：
    记录警告，仍短暂保持最后指令

  指令年龄 ≥100 ms：
    目标速度置零
    发送安全减速/抱闸指令
    安全帧继续保持50 Hz

  该门限分别容忍约3个和5个50 Hz控制周期；watchdog每20 ms检查一次，因此安全帧切换验收窗口为100–120 ms。

  ### 不建议仅修改 gate 到50 Hz

  只修改：

  update_rate: 50.0

  不能可靠解决问题，因为正常Control输出是输入回调驱动，不是该定时器重发。

  它还可能：

  - 增加状态检查和辅助话题负载
  - 仍无法保证 0x201 每20 ms发送
  - 仍保留CAN队列突发和60 ms发送循环问题
  - 把CAN协议要求泄漏到Autoware上层

  如果控制器轨迹跟踪确实需要更高频率，可以独立把控制器提升到30–50 Hz，但这和VCU心跳适配是两个问题。

  ## 验证方案

  ### 第一步：确认当前真实频率

  ros2 topic hz /control/command/control_cmd

  同时记录CAN：

  candump -t a can0,201:7FF

  需要统计：

  - ROS Control平均频率
  - 0x201平均频率
  - 相邻 0x201 最大间隔
  - 20/40/100 ms以上间隔的数量
  - 是否存在多帧突发

  ### 第二步：修改后的周期验收

  CAN周期目标：

  平均周期：20 ms
  平均频率：50 Hz
  P99周期：建议≤25 ms
  最大正常间隔：建议≤40 ms

  ROS与CAN均保持50 Hz，但不要求一条ROS消息严格对应一条CAN帧；每个CAN周期只发送当时最新值。

  ### 第三步：Byte5/Byte6验证

  在架空驱动轮或滚筒环境中：

  - 固定目标速度
  - Byte5依次测试 1、2、3、5、10
  - Byte6使用相同序列
  - 确认每个CAN周期都执行一次目标转速增减
  - Byte=1持续1秒时，验证目标电机转速变化是否为 50 r/s

  ### 第四步：超时测试

  主动停止 /control/command/control_cmd 发布：

  - 60 ms附近产生警告
  - 100–120 ms内发送零速安全帧
  - 安全帧仍保持50 Hz
  - 恢复Control后必须按明确条件恢复，避免突然使用旧速度

  ### 第五步：负载测试

  在正常Autoware全量运行、CPU/GPU高负载时重复统计：

  - 0x201周期
  - 控制指令年龄
  - 队列长度
  - 指令到CAN发送延迟
  - VCU通信故障和使能状态

  最终推荐架构是：“Autoware按控制需要发布，CAN adapter按VCU协议固定50 Hz发送最新状态”。这能同时解决报文周期、队列积压、Byte5/Byte6标定一致性和控制超时保护问题。
