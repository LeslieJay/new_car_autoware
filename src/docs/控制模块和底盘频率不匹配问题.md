• 结论：当前真正的问题不只是“Autoware 10 Hz、VCU 50 Hz”，而是 CAN driver 没有按 20 ms 周期发送 0x201。推荐在 CAN driver 内增加独立的 50 Hz 周期发送层，持续发送最新控制指令；不要单纯把 vehicle_cmd_gate.update_rate 改成 50 Hz。

  ## 当前实际行为

  ### Vehicle Command Gate

  配置中的：

  update_rate: 10.0

  主要控制 gate 的状态检查、急停检查、挡位、转向灯等定时任务。

  正常自动驾驶的 Control 指令不是由该 10 Hz 定时器发布，而是在收到上游控制指令时立即发布：

  上游控制器
    → onAutoCtrlCmd()
    → publishControlCommands()
    → /control/command/control_cmd

  因此 /control/command/control_cmd 的实际频率主要取决于上游控制器，必须实测，不能只根据 update_rate 判断。

  相关实现：src/universe/autoware_universe/control/autoware_vehicle_cmd_gate/src/vehicle_cmd_gate.cpp:387

  ### 当前 CAN driver

  CAN driver 收到一条 /control/command/control_cmd 后，编码一帧 0x201 并放入发送队列：

  Control callback → 编码0x201 → send_queue

  但发送线程循环末尾固定休眠了 60 ms：

  std::this_thread::sleep_for(std::chrono::milliseconds(60));

  因此发送线程理论最高检查频率只有约：

  1000 / 60 ≈ 16.7 Hz

  并不是 VCU 协议要求的 50 Hz。

  相关实现：

  - src/byd/all_can_ws/can_ws/src/can_driver/src/can_receiver.cpp:771
  - src/byd/all_can_ws/can_ws/src/can_driver/src/can_send.cpp:50

  ## 可能出现的问题

  ### 1. VCU报文超时

  如果 VCU 把 20 ms 当成必须满足的通信周期，当前可能出现：

  - 控制报文超时
  - 驱动使能退出
  - 速度指令间断
  - 周期性减速、抱闸或停车
  - VCU故障码或通信故障

  具体是否在20 ms后立即超时，需要确认 VCU 的超时门限。

  ### 2. Byte5/Byte6物理含义失真

  现在确认 Byte5/Byte6 表示每个20 ms周期的电机目标转速增减量。

  如果 Byte=1：

  每20 ms目标转速增加1 r/s
  1秒共50个周期
  最终增加50 r/s

  如果实际只在10 Hz收到新帧，并且 VCU仅在收到帧时执行一次增量，那么1秒只执行10次：

  期望：50 r/s
  实际：10 r/s

  加减速会变成预期的五分之一，之前基于50 Hz得到的标定系数也会失效。

  如果 VCU内部以50 Hz持续使用最后一帧，则加速度不会缩小，但仍然存在报文超时和心跳风险。这个行为需要实车或台架确认。

  ### 3. 控制延迟增加

  10 Hz Control 本身带来最多约100 ms的采样等待，再叠加当前发送线程最多约60 ms等待：

  最坏新增等待可能接近160 ms

  会影响：

  - 停车距离
  - 障碍物响应
  - 终点停车精度
  - 转向跟踪
  - 低速控制稳定性

  ### 4. CAN帧突发发送

  发送线程每60 ms调用一次 pop_all()。如果这段时间收到多条控制指令，旧指令不会被合并，而是被连续写入CAN。

  结果可能是：

  长时间无0x201 → 短时间连续多帧 → 再次长时间无帧

  平均频率即使看起来正常，周期抖动仍然很大。VCU可能依次执行已经过时的中间命令。

  ### 5. 急停更新不够及时

  普通控制指令是回调驱动的，但部分急停逻辑受 gate 的10 Hz定时器控制。再叠加CAN发送线程等待，紧急控制生效时间可能进一步增加。

  ## 推荐方案

  ### 方案一：CAN driver独立50 Hz周期发送

  这是推荐方案。

  将 ROS 控制频率和 CAN 协议频率解耦：

  Autoware Control，约10–30 Hz
          ↓
  CAN driver收到后只更新“最新控制状态”
          ↓
  独立20 ms定时线程
          ↓
  始终发送最新0x201，固定50 Hz

  核心原则：

  - Control callback只负责解析、限幅、编码并替换最新 0x201。
  - 不再把每一条 0x201 放入普通FIFO队列。
  - CAN发送线程用 steady_clock 每20 ms发送一次最新 0x201。
  - 连续收到多条Control时只保留最新一条，丢弃过期中间值。
  - 0x301、0x401等事件型报文仍可使用普通队列。
  - Byte5/Byte6随最新控制指令更新，但在五个CAN周期内重复发送相同值。
  - 不在CAN driver内插值速度；速度斜坡由VCU依据Byte5/Byte6执行。

  建议参数：

  control_frame_period_ms: 20
  control_command_warn_timeout_ms: 150
  control_command_stop_timeout_ms: 300

  ### 指令超时保护

  CAN driver应保存最后一条Control的接收时间。

  建议状态：

  指令年龄 ≤150 ms：
    50 Hz发送最新控制帧

  150–300 ms：
    记录警告，仍短暂保持最后指令

  指令年龄 >300 ms：
    目标速度置零
    发送安全减速/抱闸指令
    安全帧继续保持50 Hz

  超时时间应大于10 Hz输入的正常100 ms周期，避免少量调度抖动触发停车。

  ### 不建议仅修改 gate 到50 Hz

  只修改：

  update_rate: 50.0

  不能可靠解决问题，因为正常Control输出是输入回调驱动，不是该定时器重发。

  它还可能：

  - 增加状态检查和辅助话题负载
  - 仍无法保证 0x201 每20 ms发送
  - 仍保留CAN队列突发和60 ms发送循环问题
  - 把CAN协议要求泄漏到Autoware上层

  如果控制器轨迹跟踪确实需要更高频率，可以独立把控制器提升到30–50 Hz，但这和VCU心跳适配是两个问题。

  ## 验证方案

  ### 第一步：确认当前真实频率

  ros2 topic hz /control/command/control_cmd

  同时记录CAN：

  candump -t a can0,201:7FF

  需要统计：

  - ROS Control平均频率
  - 0x201平均频率
  - 相邻 0x201 最大间隔
  - 20/40/100 ms以上间隔的数量
  - 是否存在多帧突发

  ### 第二步：修改后的周期验收

  CAN周期目标：

  平均周期：20 ms
  平均频率：50 Hz
  P99周期：建议≤25 ms
  最大正常间隔：建议≤40 ms

  Autoware保持10 Hz时，每条ROS控制指令应对应约5帧内容相同的 0x201。

  ### 第三步：Byte5/Byte6验证

  在架空驱动轮或滚筒环境中：

  - 固定目标速度
  - Byte5依次测试 1、2、3、5、10
  - Byte6使用相同序列
  - 确认每个CAN周期都执行一次目标转速增减
  - Byte=1持续1秒时，验证目标电机转速变化是否为 50 r/s

  ### 第四步：超时测试

  主动停止 /control/command/control_cmd 发布：

  - 150 ms附近产生警告
  - 300 ms后发送零速安全帧
  - 安全帧仍保持50 Hz
  - 恢复Control后必须按明确条件恢复，避免突然使用旧速度

  ### 第五步：负载测试

  在正常Autoware全量运行、CPU/GPU高负载时重复统计：

  - 0x201周期
  - 控制指令年龄
  - 队列长度
  - 指令到CAN发送延迟
  - VCU通信故障和使能状态

  最终推荐架构是：“Autoware按控制需要发布，CAN adapter按VCU协议固定50 Hz发送最新状态”。这能同时解决报文周期、队列积压、Byte5/Byte6标定一致性和控制超时保护问题。
